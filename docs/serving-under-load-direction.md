# Serving under load: direction for the second inference act

September 24, 2026. Sol Ultra draft reviewed by the main agent and accepted as a revisable direction, not an implementation mandate. Parent review clarified the arrival-cohort versus completion-window denominator and the full cost horizon, and independently verified DSpark/DeepSpec. It extends [the inference program direction](inference-program-direction.md), [the visual consequence playbook](visual-consequence-playbook.md), and the bounded [stream-continuity manual](manual-stream-continuity.md). It does not change the existing laboratory or claim that its illustrative simulator models a production engine.

## The two-part thesis

**Part 1: Make the same intelligence cheaper to execute.** Keep the current controlled experiment: fixed policy, request content, token budget, outcomes and workload; vary scheduling, ready-prefix reuse and declared token-service rates. The scientific anchor is GPU-seconds per valid correct answer, with the current result explicitly labelled *illustrative busy work*, not allocated GPU billing or a measured kernel gain. The execution, prefix and queue films have their own useful local comparisons. Finish and judge this act on its terms.

**Part 2: Keep that intelligence usable when load arrives.** Increase concurrent demand and follow the serving loop: admission, token budget, KV ownership, cache locality, prefill/decode coexistence, draft/verify, execution, device placement, routing, release. The local question is how many *valid* requests meet declared first-token and streaming-latency targets at an offered load. This is an operational overview with one deeply inspectable interference scene, not ten invented benchmark improvements.

The acts meet at one request leaving the optimized worker. Its output glyph becomes the opening visual motif as the camera widens to show new requests arriving. An explicit “new load trace” marker prevents that visual handoff from passing Part 1's request ID or numerical result into Part 2: the workload and clock change. The visitor should be able to say: “The first experiment saved work on a fixed workload; now I can see where that saving helps, and where another bottleneck takes over.” Keep the project's existing architecture and microscope intact.

## One serving world, one visual grammar

An authored trace begins with four identifiable requests rather than a field of anonymous dots:

- **Request A, live answer:** already emitting tokens when the load arrives. Its token cadence makes interruption visible to a person waiting for a reply.
- **Request B, long document:** enters while A is streaming. Its first token competes with A's next token; this is the [stream-continuity candidate's](manual-stream-continuity.md) teaching case.
- **Request C, repeated document prefix:** arrives after B's compatible prefix has become ready. It can benefit only if retained state is present on the selected replica.
- **Request D, unrelated request:** requires its own prefill and provides a no-hit counterexample.

Those IDs, prompt-length silhouettes, arrival marks, token streams and output validity markers persist across camera changes. A request can be queued, admitted, in prefill, decoding, verifying, complete, cancelled or timed out; it cannot appear on two replicas simultaneously without an explicit move or replicated execution. The visible engine has a queue, scheduler, token-budget dial, page pool, active decode set, GPU lanes and output streams. A replica is a serving instance; a worker lane is not automatically a GPU; an expert shard belongs only to an MoE model. The default trace uses a dense small model, so expert parallelism is an explicitly labelled research branch rather than a physical stage that Request A secretly traverses.

One master cursor drives geometry, event counts and attached consequence. No independent decorative loops. Keep the existing dark observatory, Geist, crisp lines and scarce signal colors. Amber marks incoming prefill or bounded caution; blue/green identify compared service paths; coral marks a real missed interval or rejected work. Color and motion cannot be the only encodings. In a desktop frame, the serving loop remains spatially visible while one mechanism brightens; the request path never resets between scenes. On a narrow screen, use a labelled horizontal diagram viewport with readable type. A user may jump to any beat, scrub backward, pin a request or inspect an event; autoplay never becomes a prerequisite for comprehension.

The authored pass should be a small number of **camera moves through one system**, rather than ten equal cards:

1. **Demand appears:** A is streaming; B enters, while C and D are visible as later arrivals on the same demand trace. A queue grows under a bounded token and memory budget.
2. **Admission decision:** the scheduler admits what fits, leaves one request waiting, and exposes why. A compact held comparison distinguishes “worker available” from “KV room available.”
3. **Stream interference:** B's long prefill interrupts A's tokens. The accepted stream-continuity candidate, if review passes, supplies a real event-derived baseline/chunked comparison, then holds the longest gap and B's first-token cost separately.
4. **Memory and locality:** B's prefix becomes ready; C reuses it only on the right replica. D remains cold. A's live pages eventually release. The avoided prefill segment is bracketed on C's timeline.
5. **Remaining decode work:** a draft/verify window offers accepted and rejected tokens, and a compute tile shows the target steps still needed. Inspection can switch to a loss case where drafting costs more than it saves. No claim that both optimization paths produce an additive win.
6. **Placement and recovery:** widen from one engine to replicas, then show the distinct tensor/pipeline possibilities and an MoE-only expert branch. Route C using both queue and cache state; cancellation releases D's pages. Show communication and warmup edges before promising scale.
7. **Service outcome:** the same arrival cohort resolves into three visible populations: valid and within both latency targets, valid but late, and invalid or unfinished. The foreground question is how many offered requests *eventually qualify* under the declared deadlines, shown as attainment and arrival-cohort goodput; a numeric value appears only after the full event and quality contract below exists. Its cost and quality gates remain adjacent. A held loss case makes clear that more raw tokens per second need not produce more acceptable responses.

At each reveal, keep baseline geometry, brighten the changed object, then hold the result for roughly three seconds before carrying its state forward. Holds are pacing hypotheses to verify in a browser. They do not require a fixed watch time; all states are directly selectable. Avoid recurring full-screen blur, a fixed essay sidebar, a chat transcript that repeats the diagram, and an equal-priority metric wall.

## Component contracts

These contracts set the visual and scientific boundaries. “Overview” means a causal schematic with inspectable events; “deep” means a numerical model whose calculations and counterexamples pass review. Existing microscope graphics may supply geometry but do not automatically upgrade an overview to a measured result.

### 1. Load arrives: preserve the offered workload

- **State and trigger:** A's output cadence is stable; B's long input, C's shared context and D's unrelated prompt arrive at fixed timestamps. A later burst increases offered arrivals without changing individual request specifications.
- **Visual move and consequence:** zoom from a few identifiable users to grouped demand, preserving the first four. Show a queue forming before the GPU fabric; a count label says *requests offered*, never “active GPU nodes.” The practical question is whether A continues streaming and whether B receives a first token on time.
- **Boundary:** define arrival times, prompt/output lengths, cancellation and deadline before rendering outcomes. A 1,000-agent graphic may group requests but proves neither 1,000 concurrent executions nor a 10,000-request benchmark. Quiet load is a counterexample where queue optimization has little effect.
- **Evidence:** current 1,000-request zoom is an **illustrative execution replay** with two serial workers. Any new request trace is a separate versioned scenario until a common simulator exists.

### 2. Admission and continuous batching: show a decision each iteration

- **State and trigger:** runnable requests, already decoding requests, remaining token budget and available KV space are visible at a scheduling boundary. B cannot be admitted merely because one worker looks empty.
- **Visual move and consequence:** move a request through a gate only when both budgets permit; then refill the next iteration from the live queue. The current “start when a worker is free” lesson remains legible as its own first-principles comparison. In Part 2, token-level admission is a distinct, deeper mechanism.
- **Boundary and tradeoff:** Σ scheduled tokens per step ≤ declared batch-token budget, and committed memory ≤ declared capacity. Decode priority protects existing streams but can postpone B's first token. If there is no waiting work, an idle worker is not wasted scheduling. Real engine scheduling also depends on capacity and policy; do not call the existing FIFO two-worker result physical continuous batching. [vLLM's scheduler](https://docs.vllm.ai/en/latest/api/vllm/v1/core/sched/scheduler/) uses token budgets and KV allocation together.
- **Evidence:** microscope **illustrated**; current queue experiment **modeled as two serial workers**; iteration-level policy **planned**, with the stream-continuity candidate under separate review.

### 3. KV capacity and paged memory: show ownership before benefit

- **State and trigger:** page tiles carry request owner, occupied token range, free status and, when applicable, retained-cache status. C arrives when the pool is nearly full.
- **Visual move and consequence:** draw C's block table referencing pages; show A's pages release only when A finishes or is safely cancelled. If no pages are available, the admission gate visibly holds C even if compute is free. The user sees the cause of a delayed first token.
- **Boundary and tradeoff:** distinguish *reserved slots* in the stream-continuity teaching model from actual page allocation, reference counts, fragmentation and eviction. Paging improves allocation flexibility; it does not by itself save prefill compute. A full pool can force waiting, eviction or preemption depending on an engine policy, and none of those may be implied without modeling them. [vLLM's KV manager](https://docs.vllm.ai/en/latest/design/prefix_caching/) documents block ownership and eviction separately.
- **Evidence:** paged-memory microscope **illustrated**; candidate serving model has only **modeled reservations**; page pressure/eviction **planned**.

### 4. Prefix locality and reuse: make the cold work disappear precisely

- **State and trigger:** C shares a token-identical, compatible prefix with B after B's prefill has completed. The prefix has a ready timestamp, block IDs and replica owner. D shares none.
- **Visual move and consequence:** C's route forks to a warm replica or a colder but shorter queue. On the warm path, cached block pointers join C; only C's unmatched suffix traverses prefill. Highlight those avoided tokens and C's earlier first-token event in the same coordinate system. D shows no dividend.
- **Boundary and tradeoff:** reuse requires a valid, ready match and available retained state; cross-tenant isolation and replica locality matter. A warm but overloaded replica may lose to a cold one after queue wait. Do not count saved prefill as saved decode, a retrieved answer, or free cross-replica KV transfer. [vLLM's prefix-cache design](https://docs.vllm.ai/en/latest/design/prefix_caching/) and [SGLang's RadixAttention](https://www.lmsys.org/blog/2024-01-17-sglang/) motivate the branch.
- **Evidence:** existing paired-prefix result is **modeled and illustrative** for ready reuse; replica-aware hit/miss/eviction outcomes are **planned**.

### 5. Prefill and decode: expose the human-visible stall

- **State and trigger:** A's tokens have emitted at known timestamps; B's 128-token document arrives. The single engine must decide how much of B to read while A needs its next token.
- **Visual move and consequence:** on one absolute axis, a full prefill makes a hole in A's token marks. Chunked prefill breaks B's read into pieces and inserts more A emissions. A bracket shows A's longest silence; a separate marker shows B's first token. The visitor sees both users' experience.
- **Boundary and tradeoff:** first-token latency and output-token gap need not improve together. Smaller chunks can add iteration overhead and postpone B. Disaggregation is a separate placement option with KV transfer and coordination cost, not another name for chunking. [vLLM tuning](https://docs.vllm.ai/en/latest/configuration/optimization/) and [DistServe](https://arxiv.org/abs/2401.09670) support this distinction.
- **Evidence:** a four-request deterministic **candidate is built but unmounted** under the [manual](manual-stream-continuity.md). Source and model tests have passed; browser visual and interaction acceptance remains outstanding. Its times are illustrative milliseconds, not GPU telemetry.

### 6. Speculative draft/verify: reveal accepted work and wasted verification

- **State and trigger:** a decoding request has a target distribution/greedy next-token rule, a draft proposal and a batch with limited target-verification slots.
- **Visual move and consequence:** one draft ribbon proposes several tokens. The target accepts a prefix, rejects at the first mismatch and supplies a corrected continuation; accepted tokens join the same output stream. In a second setting, a long low-confidence suffix occupies verification slots but yields few accepted tokens, making the loss case visible under load. A compact inspector can change draft length or acceptance pattern.
- **Boundary and tradeoff:** benefit = target passes avoided minus draft, verification and scheduling overhead under a declared workload. Greedy toy verification can preserve a fixed greedy target sequence; distributional equivalence for stochastic decoding requires the appropriate correction algorithm, which the current microscope does not prove. Acceptance often changes with context and load. [DeepSeek's DSpark paper](https://arxiv.org/abs/2607.05147) specifically studies confidence-scheduled verification to avoid low-value suffix work in high-concurrency serving; [DeepSpec](https://github.com/deepseek-ai/DeepSpec) is the authors' draft-training/evaluation code. DSpark is a research reference here, **not a technique implemented by this portfolio**.
- **Evidence:** current speculative SVG **illustrative**; draft/verify accounting, quality-preserving sampler and loss case **planned**. Do not import DSpark's published performance figures as this project's results.

### 7. Kernel execution and quantization: separate faster arithmetic from changed arithmetic

- **State and trigger:** the target still owes an attention/matmul/decode step after scheduling and any accepted draft. A compute tile shows launches, data movement and kernel duration for that same work.
- **Visual move and consequence:** inspect one token across baseline and optimized execution lanes, preserve token identity, then show the released compute interval admitting another request. A precision toggle changes the bytes moved and memory fit geometry, with a quality-gate marker that can fail.
- **Boundary and tradeoff:** the existing film changes declared prefill/decode rates; it does **not** attribute speedup to CUDA, TensorRT, FlashInfer or a particular kernel. Quantization can reduce memory traffic or make a checkpoint fit, but precision, dequantization overhead, hardware support and answer quality can change. The “identical cognition” claim cannot be carried through a lower-precision checkpoint without a matched quality test. [FlashInfer](https://arxiv.org/abs/2501.01005) and [TensorRT-LLM quantization guidance](https://nvidia.github.io/TensorRT-LLM/performance/performance-tuning-guide/fp8-quantization.html) are implementation lineage, not measured evidence for this site.
- **Evidence:** execution-rate sensitivity **modeled and illustrative**; quantization and profiling microscope **illustrative**; attributed kernel measurements and independent quantized-quality evaluation **unavailable/planned**.

### 8. Tensor, pipeline and expert parallelism: topology changes the graph

- **State and trigger:** the model or desired capacity no longer fits a useful single-device operating point. A branch selector chooses replica/data parallel, tensor split of one layer, or layer groups in a pipeline. Only an MoE reference branch exposes expert routing.
- **Visual move and consequence:** one request fans through the selected topology while wires light only when an activation or collective actually crosses a device boundary. Pipeline cells reveal fill/drain bubbles; tensor split reveals a synchronization edge; replicas handle distinct requests. In the MoE branch, token-to-expert dispatch crosses an all-to-all fabric. Show the critical path and the communication slice before the result readout.
- **Boundary and tradeoff:** adding devices can raise capacity or enable a large model, but may add communication, bubbles, idle shards and allocated GPU cost. **[Qwen3-4B is dense](https://github.com/QwenLM/Qwen3); expert parallelism is not a valid “same-checkpoint” stage for it.** DeepSeek's [published inference overview](https://github.com/deepseek-ai/open-infra-index/blob/main/202502OpenSourceWeek/day_6_one_more_thing_deepseekV3R1_inference_system_overview.md) describes EP, phase-specific placement and balancing for its own MoE stack. [vLLM's data-parallel](https://docs.vllm.ai/en/latest/serving/data_parallel_deployment/) and [expert-parallel](https://docs.vllm.ai/en/latest/serving/expert_parallel_deployment/) guides describe distinct deployment paths. These examples explain design space, not this project's deployment.
- **Evidence:** tensor/pipeline SVGs **illustrative**; physical cluster topology, interconnect cost and EP execution **not modeled**. Label the MoE branch “research lineage / different model.”

### 9. Routing and lifecycle: put the gained capacity to work

- **State and trigger:** two replicas have different queues, KV occupancy and cached prefixes. C arrives; D later cancels. A new replica may be warming.
- **Visual move and consequence:** route C by an explicit decision surface combining estimated wait, cache locality and admission capacity. If warm-prefix affinity wins, show its cached pages; if a shorter cold queue wins, show the re-prefill cost. D's cancellation stops scheduled future work and releases owned pages, after which another request enters. Warmup appears as a real unavailable interval, not instantaneous new capacity.
- **Boundary and tradeoff:** “least queued” can throw away locality; “always warm” can overload a hot replica. Moving a live decode needs KV transfer and may be worse than waiting. Track request ownership, cancellation and page release in one event trace; avoid unexplained teleportation or a decorative “auto-scale” flash. [vLLM's data-parallel deployment guidance](https://docs.vllm.ai/en/latest/serving/data_parallel_deployment/) notes per-engine independent KV caches and state-aware balancing; [TensorRT-LLM disaggregated serving](https://nvidia.github.io/TensorRT-LLM/features/disagg-serving.html) makes KV exchange an explicit cost.
- **Evidence:** existing lifecycle and routing diagrams **illustrative**; cache-aware multi-replica placement, transfer and warmup **planned**.

### 10. Goodput: let the service, quality and cost constraints judge the ending

- **State and trigger:** every offered request retains arrival, first-token, per-token, completion, cancellation, validity and resource-accounting fields. Its outcome must be classifiable from those events, not from the color chosen by an animator.
- **Visual move and consequence:** the request field resolves to within-SLO valid completions, valid but late completions, invalid completions and unfinished/timeouts. Select a missed request to trace backward to the exact queue, prefill, decode, memory or verification event that caused it. Highlight the marginal requests admitted by an intervention, then separately show any newly late requests. The user learns why aggregate throughput alone can mislead.
- **Boundary and tradeoff:** use the exact fixed-cohort definition below. A configuration may improve tokens/s and worsen streaming gaps, quality, allocated GPU cost or fairness. Profiling identifies the critical interval; it is not an additional performance gain. No final numeric arrival-cohort goodput claim until all required events and a quality evaluator exist.
- **Evidence:** full constrained-goodput comparison **planned**. Current results offer illustrative busy-work and queue views, not this end-to-end service measurement.

## The arithmetic contract for any later result

Choose an arrival window **[t0, t1)** of length **W seconds** and a fixed request cohort whose arrivals fall inside it. Declare a per-request terminal timeout before comparing interventions, and a common accounting horizon **H** long enough to observe the latest possible cohort deadline after t1. Observe each request through completion, cancellation or timeout by H. Declare the checkpoint, hardware/replica count, prompt and sampling policy, arrival trace, output-length distribution, KV capacity, cache state, SLOs and verifier before replaying any intervention.

For each request `r`, define `TTFT(r) = first_token(r) - arrival(r)`; `gap_max(r)` is the maximum observed interval between consecutive delivered output tokens after the first, with an explicit policy for one-token or zero-token responses; `valid(r)` comes from an independent task/output check. A qualifying response must complete successfully, satisfy `TTFT(r) <= T_first`, satisfy `gap_max(r) <= T_gap` (or a declared TPOT rule, not an interchangeable label), and pass `valid(r)`. A cancelled, timed-out or missing response remains in the offered denominator and does not qualify. Then:

```text
offered load = cohort arrivals in [t0,t1) / W                   requests per second
arrival-cohort goodput = cohort responses qualifying by H / W  requests per second
attainment = cohort responses qualifying by H / cohort arrivals fraction
```

**Arrival-cohort goodput is a yield normalized by the arrival-window length.** Some qualifying responses may finish after t1. It is not the number of completions *during* W, nor a stationary throughput estimate. Report it with offered load and attainment. A literal completion-window rate needs a separately declared window **[u0, u1)**: completions with finish times inside that window divided by `u1-u0`; a qualified completion-window rate counts only completions that also pass the declared SLO and verifier. Requests admitted before u0 may finish inside it. Report warmup, drain and offered demand if claiming steady-state capacity, and do not substitute either completion-window rate for this fixed-cohort result.

State whether the SLO applies per request, at p95/p99, or as an attainment target; never slide between these definitions. Show p95 TTFT and p95 token gap only with their sample size and treatment of incomplete requests. **Cost follows the cohort through H, not only through t1.** For an isolated cohort replay, sum busy device time or actual allocated-GPU intervals over **[t0, H]**, including attributable work and allocation during post-t1 drain; include draft, verifier and KV-transfer GPU work where applicable. If hardware is released before H, its allocation ends at the recorded release event. If other traffic shares the devices, predeclare an attribution rule or report whole-service cost rather than assigning unseparable idle allocation to this cohort. Never charge only W while counting answers produced in the drain. GPU-seconds per *valid correct answer* divides that declared cost by all valid correct cohort answers observed by H; GPU-seconds per *qualifying answer* divides by the stricter SLO-and-quality count. Label the chosen denominator and disclose omitted non-GPU costs. The current Part 1 model cannot simply be summed with a Part 2 result. [DistServe](https://arxiv.org/abs/2401.09670) motivates simultaneous first-token and generation-rate constraints; [research on SLO/goodput definitions](https://arxiv.org/abs/2410.14257) cautions that the chosen metric can reward pathological token delivery or dropped requests. Our fixed-cohort definition keeps dropped requests visible.

## Evidence and applicability layer

Every public view needs one always-readable status such as **Illustrative serving trace**. The event inspector may then list component-level labels with clear referents: **implemented in site**, **scenario-modeled**, **profiled on hardware**, **measured on hardware**, **planned**, or **published external reference**. Do not mark an SVG “implemented” if only the rendering exists while its runtime mechanism is absent. A measured tag requires a raw artifact, command/config, hardware, model and workload identity, units and analysis script. No such artifacts are supplied for the planned serving-wide comparisons.

The public narrative may name vLLM, SGLang, TensorRT-LLM, FlashInfer, DeepSeek and DSpark as documented systems or research lineage after the mechanism is understood. These names must never imply Yash built, ran or benchmarked their paths. DeepSeek's DSpark is a confirmed 2026 method for semi-autoregressive drafting with confidence-scheduled verification, documented in its [paper](https://arxiv.org/abs/2607.05147) and [DeepSpec repository](https://github.com/deepseek-ai/DeepSpec). The name also appears in unrelated third-party projects; use the paper title or “DeepSeek DSpark” when disambiguation matters. Its published performance remains its authors' result. Do not quote a speedup in the portfolio without its workload, batch and comparison baseline, and never relabel it as ours.

## Audience and purpose

A technically informed visitor should first see a consequence, then be able to inspect the engineering that caused it. Architecture establishes the system; the microscope exposes its mechanisms; the laboratory puts those mechanisms under pressure. Keep the existing architecture and microscope intact.

The shared argument is two independent optimization surfaces: improve a reasoning policy, and improve execution of a fixed policy. Do not imply that a simulated presentation establishes completed model training or hardware measurements.

Inference's working frame is **serving the same cognition under load**. Scheduling, reuse, and execution are distinct interventions within that problem. Prefix reuse is important because a workload supplies reusable work, not because caching must be the narrative's headline. Post-training's frame is **how a policy changes, and how a fixed policy uses additional thought**. Training and inference must remain visibly separate.

## Decisions, not a universal grammar

- Preserve request/task identity and comparison coordinates when they carry understanding.
- Give each component its own spatial argument. Equal bar lengths with earlier starts explain scheduling; shared state explains reuse; synchronized completion and an exposed residual interval explain execution.
- Spotlighting changes priority, never the technical substance available to inspect.
- Film first, direct inspection immediately available. No mandatory watch time.
- Reveal the relevant result after its cause is visible. Do not keep an unrelated full-cohort dashboard beside every scene.
- Motion represents a computed state or an intentional attention cue. No atmospheric token pulses presented as execution evidence.
- Treat speculation and cluster placement as candidate later scenes, not implemented results. They require their own cost models, failure cases, and inspections. Do not extend today's additive accounting to them by assertion.

## First resolved scene: Execute efficiently

Hypothesis: a finished answer beside a still-running reference is a stronger opening than a speedup headline. The viewer must witness the interval that was saved before seeing its aggregate consequence.

1. Establish one matched request, unchanged token count and computed input. One common service-time axis.
2. Run both executions. Optimized completion is a timed event, not an arbitrary animation breakpoint. Hold that result; continue only the reference tail in amber.
3. Bracket the residual interval. Keep total busy work separate from wall-clock or queue time. Both coincide only for the isolated single-worker service example.
4. Expand to repeated identical service profiles: 1, 10, 100, 1,000 requests. Additive busy-work curves, zero-based axes, no invented exponential shape or new hardware claim.
5. Change the question from work to waiting. Replay heterogeneous fixed service profiles on two abstract serial workers at increasing arrival rates. Show p95 response latency and waiting, including an overloaded counterexample. The queue is recomputed, not multiplied from one-request savings.
6. Return to the same 96-task cohort and expose the execution-only delta. Prefix reuse remains held fixed; its savings cannot be attributed again to faster execution.

## Scope and measurement boundary

The isolated service and repeated-request comparison use a matched task from existing simulated runs. The load sweep cycles the existing 96 service profiles with fixed cache outcomes, under newly declared arrivals. It is a service-time sensitivity model, not a vLLM batching or cache-readiness experiment. Two abstract serial workers, FIFO admission, no batching, network, memory contention, distributed coordination, idle allocation or verifier cost. No measured GPU or actual generated text.

One transport clock drives chapter advancement, service progress, scene transitions, and result reveals. Seek reverses all those states. Reduced motion shows the settled conclusion with every scene directly selectable. Pause/offscreen/tab-hidden must stop progression.
